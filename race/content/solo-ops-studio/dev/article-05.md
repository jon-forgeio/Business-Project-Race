# Build a Client Onboarding Packet Once, Reuse It on Every Project

Onboarding a new client is the same work every time: collect information, agree scope, explain how you work, get access to files, set dates. Most freelancers rebuild it from scratch in a long email thread, and something always gets missed. A reusable onboarding packet turns that thread into a folder you copy, fill and send.

This article lists the seven parts of a packet, what goes in each, and how to store it so setup for a new client takes minutes rather than an afternoon.

## The folder structure

Start with one template folder. For each new client, duplicate it and rename it with the client and project name. Inside:

```
00-start-here
01-intake
02-scope
03-how-we-work
04-access-and-assets
05-schedule
06-invoices
```

Numbered prefixes keep the order fixed in any file browser. The client sees the same structure on every project, and so do you.

## Part 1: Start here (one page)

A single page the client reads first. It covers:

- what happens in the first week, in three or four numbered steps;
- what you need from them and by when;
- how to reach you and your usual response time;
- where each part of the packet lives.

Keep it to one screen. Everything else links from here.

## Part 2: Intake questions

A short questionnaire the client fills in before kickoff. Good intake questions are about outcomes and constraints, not just deliverables. A few to start with:

- What problem are we solving, in one sentence?
- Who is the end audience?
- What does a good result look like, and how will you judge it?
- Who makes the final decision, and who else reviews?
- What examples do you like, and why?
- Is there a hard deadline, and what is driving it?

Send it as a form or a plain document. Read the answers before the kickoff call, so the call is for clarifying, not for collecting.

## Part 3: Scope summary

A plain-language summary of what you agreed, written so both sides can point at it later:

- deliverables, with quantities and file formats;
- number of revision rounds and how feedback is sent;
- what is excluded, written down explicitly;
- payment schedule and what triggers each payment;
- who owns the final files, and when that transfers.

This is not a contract. If you use a contract, the scope summary should match it, and the contract should be your own, reviewed by a qualified professional where needed.

## Part 4: How we work

This is the page that prevents most friction. Write down:

- which channel you use for what (for example, email for decisions, a shared doc for feedback);
- your working hours and time zone;
- when you send status updates, and what they contain;
- how change requests are handled, including that new items are quoted before they start.

Clients rarely object to a clear process. They object to surprises.

## Part 5: Access and assets

A checklist of everything you need from the client: brand files, existing copy, logins to tools, sample data. For each item, note who provides it and the date you need it.

Ask for access to be shared through the tool's own invite or sharing feature, or a secure password manager, never in plain email. Note in the packet how access will be removed at the end of the project.

## Part 6: Schedule

A short table with the key dates:

| Milestone | Date | Who |
|-----------|------|-----|
| Intake returned | | Client |
| Kickoff call | | Both |
| First draft | | You |
| Feedback due | | Client |
| Final delivery | | You |

Add one line under it: if feedback arrives late, the later dates move by the same number of days. Agreeing to that at the start is much easier than negotiating it mid-project.

## Part 7: Invoices

An empty folder, plus a one-line note on how invoices are sent and when they are due. Keeping invoices in the same folder as the project makes the end-of-project check simple.

## Using the packet

1. Duplicate the template folder and rename it.
2. Fill in names and dates in "Start here", "Scope" and "Schedule".
3. Send the client the folder link and the intake questions.
4. Hold the kickoff call after the intake comes back.
5. At the end of the project, archive the folder and remove any access you were given.

Every time a project surfaces a question the packet did not answer, add the answer to the template, not just to that client's copy. The template improves with each project.
